索引不是「加了就快」的开关，它本质上是拿空间和写入成本换查询速度。

## 一句话总结

索引像书的目录：不用翻完整本书，就能定位到内容在哪一页。数据库用的目录结构通常是 B+ 树，所以查询时间从「跟数据量成正比」变成「跟树的高度成正比」。

## 核心内容

- 没有索引时，查询要逐行扫描（全表扫描），数据越多越慢
- 有索引时，从根节点往下走几层就能定位，100 万行通常也只要 3～4 次磁盘访问
- 代价：索引本身占空间；每次写入（增删改）都要顺带维护索引，所以会变慢
- 联合索引遵循「最左前缀」：`(a, b)` 能加速 `where a=?` 和 `where a=? and b=?`，但 `where b=?` 用不上
- 查询条件里对索引列做运算（`where year(created) = 2026`）通常会让索引用不上
- 索引不是越多越好，写多读少的表上尤其要克制

## 例子

```sql
-- 慢：全表扫描
select * from notes where tags = '数据库';

-- 建索引后变快
create index idx_notes_tags on notes (tags);

-- 联合索引，注意字段顺序：区分度高的放前面
create index idx_notes_author_time on notes (author_id, created_at);

-- 能用到上面的索引
select * from notes where author_id = 7 and created_at > '2026-01-01';

-- 用不到（没有 author_id 这个前缀）
select * from notes where created_at > '2026-01-01';
```

想看优化器到底用了哪个索引，用 `explain` 看执行计划，别靠猜。

## 我踩过的坑

- 以为建了索引就一定生效，实际因为类型不一致（字符串列拿数字去比）退化成全表扫描
- 在低区分度的列上建索引（比如性别），效果几乎没有
- 忘了索引要占空间，一张大表加几个索引，磁盘涨得比想象快
